# 섹션 순서 레시피

셸은 **빈 골격**입니다. 막히는 건 CSS가 아니라 *"무슨 섹션을 어떤 순서로 놓지"* 입니다.
아래는 실제로 써먹은 배치 세 가지입니다. 그대로 쓰지 말고 **덜어내면서** 쓰세요 — 섹션이 많은 게 좋은 게 아닙니다.

> 셸을 문서 유형별로 복제하지 마세요. 팔레트 엔진이 N벌이 되면 고칠 때 N군데를 고쳐야 합니다.
> **파일은 하나, 순서만 골라 쓰는 게 이 문서의 목적입니다.**

---

## A. 비교 · 우수성 리포트

"우리 게 왜 나은가"를 증명하는 문서. 사내 공유·영업 자료.

| § | 섹션 | 핵심 블록 |
|---|---|---|
| 00 | **결론부터** — 하고 싶은 말 한 문장 + 지표 타일 4개 | `.verdict` `.tiles` |
| 01 | **비교 대상** — 같은 기준으로 N가지 방식을 나란히 | `.tw > table` |
| 02 | **왜 갈리는가** — 우위가 나오는 *단 하나의 지점* | `.cal.key` |
| 03·04 | **예시** — 실제로 갈린 사례. 한 섹션에 하나씩 | `.cmp.two` `.quote` |
| 05 | **우리만 하는 것** — 기능별로 `.feat` 를 쌓는다 | `.feat` `.chain-flow` |
| 06 | **기능 매트릭스** — 경쟁 대비 ✓/✗ | `table.matrix` |
| 07 | **경계** — 어디까지가 우위이고 어디부터 아닌지 | `.cal.key` |
| 08 | **근거 강도** — 주장별 표본과 강도 | `.tw > table` |
| 09 | **종합** | `.verdict` |

**이 유형에서 제일 자주 망가지는 곳**

- 표지 타일에 **단건 수치**를 올린다. `9.6×` 같은 배수는 보드 하나에서 나온 값이라
  표본이 바뀌면 무너집니다. 타일은 **구조 명제**로 채우고(있다/없다, 고정/변동),
  단건 수치는 본문에서 *사례*로 쓰세요.
- §07 경계와 §08 근거 강도를 뺀다. 둘 다 있어야 나머지가 믿깁니다.
  "다 좋다"만 있는 리포트는 첫 질문이 "그래서 안 되는 건 뭔데요?" 입니다.

## B. 기술 설명 자료 (외부 전문가용)

변리사·감사·외주 등 **그 분야 전문가에게 사실을 넘기는** 문서. 설득이 아니라 전달.

| § | 섹션 | 핵심 블록 |
|---|---|---|
| 00 | **읽는 법** — 이 문서를 쓴 사람의 한계 + 용어 정리 | `.cal.honest` `.tw` |
| 01 | **발단** — 누가 무엇을 물었고, 무엇을 확인했나 | `.tw` `.chain-flow` |
| 02 | **현황** — 지금 상태와 참고할 일정 | `.verdict` `.tiles` |
| 03 | **기능 설명** — 동작 + 고정 상수표 | `.feat` `.tw` |
| 04 | **사전 조사** — "참고용"임을 명시 | `.tw` |
| 05 | **차이점** — 우리가 다르다고 보는 것 + 정정 고지 | `.tw` `.cal.honest` |
| 06 | **세부 특징** — 근거와 함께 | `.tw` |
| 07 | **실측** — 파일·줄 단위까지 | `.tw` `.cal.key` |
| 08 | **숫자 신뢰도** — 써도 되는 것 / 안 되는 것 | `.cmp.two` |
| 09 | **사실 정리** — 판단은 상대에게 넘긴다 | `.tw` `.cal.honest` |

**이 유형의 규칙 — A와 정반대입니다**

- **전문 용어를 쓰지 마세요.** 상대가 전문가라고 그 사람 용어를 흉내 내면,
  틀리게 쓴 한 단어가 문서 전체의 신뢰를 깎습니다. §00에 *"이 뜻으로 썼습니다"* 표를 두고
  본문은 일상어로 씁니다.
- **질문을 늘어놓지 마세요.** 전담 전문가는 이미 판단 축을 갖고 있습니다.
  사실을 주고 판단은 넘기면 됩니다. 질문 목록은 상대의 시간을 뺏는 형식입니다.
- **정정 고지를 반드시 남깁니다.** 초안에서 틀렸던 것, 폐기한 수치.
  실제와 다른 내용이 명세·감사 문서에 들어가면 사고가 됩니다.

## C. 실험 · 측정 보고

"고쳐봤더니 이랬다"를 남기는 문서.

| § | 섹션 | 핵심 블록 |
|---|---|---|
| 00 | **결론** — 무엇이 움직였고 무엇이 안 움직였나 | `.verdict` `.tiles` |
| 01 | **가설** — 착수 전 무엇을 기대했나 | `.cal.key` |
| 02 | **방법** — 표본·환경·재현 명령 | `.tw` |
| 03 | **결과** — 전/후 대조 | `.tw` `.cmp.two` |
| 04 | **원인** — 왜 그렇게 나왔나 | `.feat` |
| 05 | **반증·정정** — 틀렸던 판단과 폐기한 수치 | `.cal.honest` |
| 06 | **한계** | `.cal.honest` |
| 07 | **다음** | `ul` |

**§05를 절대 빼지 마세요.** 측정 보고의 값어치는 *"이건 아니었다"* 에서 나옵니다.
가설이 다 맞은 보고서는 대개 측정을 안 한 보고서입니다.

## 어떤 블록을 언제 쓰나

| 하고 싶은 것 | 블록 |
|---|---|
| 한 문장으로 못 박기 | `.verdict` + `.big` + `.hl` (강조는 한 구절만) |
| 숫자 4개로 요약 | `.tiles` — `.s` 에 **근거·표본을 반드시** 적는다 |
| N개를 같은 기준으로 비교 | `.tw > table`, 우리 쪽은 `tr.me` |
| 되는 것 vs 안 되는 것 | `.cmp.two` + `.pane.win` / `.pane.fail` |
| 기능 하나를 설명 | `.feat` + `h4` + `.k`(상수) + `.why`(단계) |
| 순서·경로를 보여주기 | `.chain-flow` + `.hop` |
| 가장 중요한 논지 | `.cal.key` |
| **못 한 것 · 틀린 것 · 쓰면 안 되는 수치** | `.cal.honest` ← 없으면 문서가 의심받는다 |
| 근거가 약한 수치임을 표시 | `.s` 안에 `<span class="n1">n=1 단건</span>` |

---

## 공통 — 문서 유형과 무관하게

1. **약한 근거는 약하다고 쓴다.** `n1` 태그와 근거 강도 섹션이 그 장치입니다.
   숨긴 약점은 발표 중에 질문으로 돌아옵니다.
2. **정정 고지를 남긴다.** 중간에 틀렸던 판단을 지우지 말고 `.cal.honest` 에 적으세요.
   "이건 폐기했습니다"가 있는 문서가 더 믿깁니다.
3. **섹션은 9개를 넘기지 않는다.** 넘으면 읽는 사람이 순서를 잃습니다.
   프레젠테이션 모드에서 슬라이드는 더 많아도 됩니다 — `.sl` 을 쪼개면 되니까요.
4. **마지막에 [verify-badge](../verify-badge/) 를 붙인다.** 사용 범위 배너 + 검증 이력.
   문서의 팔레트 변수를 물려받아 테마를 그대로 따라갑니다.
