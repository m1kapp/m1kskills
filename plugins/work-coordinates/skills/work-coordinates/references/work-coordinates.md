# 작업 좌표 정본

사용자 응답은 사용자가 다른 언어를 요청하지 않는 한 한국어로 작성한다.

## 작업 상태

- 모든 실질적인 작업 세션에는 작업 좌표를 적어도 한 번 남긴다.
- 실제 상태 변경, 완료, 중단, 인계, 상태 질문에는 최종 응답 끝에 작업 좌표를 둔다.
- 상태가 바뀌지 않은 짧은 문답에는 생략할 수 있다.
- 분석·리뷰·상태 답변은 한 문장 판정으로 시작한다. `확인됨`, `추론`, `아직 모름`을 필요한 곳에 구분한다.
- 사용자가 `다음`이라고 하면 이미 승인된 범위에서 다음 관측 가능한 게이트까지 실제로 진행한다. 새 권한이나 결과를 바꾸는 결정이 필요할 때만 멈춘다.
- 사용자가 `실제로`, `진짜`, `직접`을 강조하면 가능한 가장 바깥 경계에서 실행하고 `환경 · 입력/행동 · 관측 결과`를 남긴다. 실행하지 못하면 이유와 대신 확인한 경계를 밝힌다.

## 북극성과 게이지

- `목표`는 여러 세션을 관통하는 북극성이다. 즉시 수행한 작은 작업으로 바꾸지 않는다.
- 이전 작업 좌표가 있으면 목표 문구와 게이지를 그대로 계승한다.
- 목표를 바꾸거나 완료한 뒤 새 이니셔티브를 시작할 때만 목표를 바꾼다.
- 게이지는 `█`와 `░` 다섯 칸 및 달성률로 표시한다.
- 메시지 수가 아니라 검증 가능한 이정표를 통과했을 때만 게이지를 올린다.
- `현재`에는 목표까지 도달한 수준, 근거, 남은 거리를 적는다.
- `다음`에는 목표에 가장 가까워지는 행동 하나만 적는다. 없으면 `없음`으로 쓴다.
- 100%여도 전달할 미커밋 또는 미게시 변경이 있으면 `다음`은 `커밋 → PR`로 쓴다.

## 검증과 결과

- `테스트`에는 사용자가 그대로 복사할 정확한 프롬프트나 동작과 관측 가능한 기대 결과를 함께 적는다.
- UI는 클릭 경로, API는 요청값, 대화형 기능은 완전한 입력 문장을 쓴다.
- 아직 배포되지 않았으면 `배포 후` 조건을 명시한다.
- 수동 검증이 의미 없으면 `해당 없음 · 이유`로 쓴다.
- `결과`에는 실제로 남은 URL, 절대 파일 경로, 커밋만 최대 3개 적는다. 없으면 `없음`으로 쓴다.
- 모든 결과는 짧고 설명적인 라벨을 가진 GitHub Flavored Markdown 링크 `[라벨](대상)`로 쓴다. 맨 경로, 맨 URL, 백틱 경로는 금지한다.
- 로컬 파일은 `[라벨](/절대/경로)`로 쓴다. 대상 경로에 공백이나 괄호가 있으면 반드시 `[라벨](</절대/경로 with spaces>)`처럼 링크 대상을 `<...>`로 감싼다. 라벨이나 대상 안에 백틱을 넣지 않는다.
- PR·이슈·배포·문서는 전체 `https://` URL을 링크 대상으로 쓴다. 커밋은 원격 URL을 만들 수 있으면 커밋 전체 URL로, 아니면 `[저장소 · abc1234](/저장소/절대/경로)`처럼 저장소를 열 수 있게 쓴다.
- 결과를 쓴 뒤 렌더러에서 클릭 가능한지 문법을 자체 점검한다. 특히 공백이 든 로컬 경로는 링크가 깨지기 쉬우므로 그대로 노출하지 않는다.

## 증거 기반 디버깅

변경 전에 다음 순서로 진행한다.

1. `증상`: 사용자가 겪는 실패를 관측 가능한 문장으로 고정한다.
2. `가설`: 가능성과 판별 비용으로 우선순위를 매긴다.
3. `관측`: 가설을 가르는 최소 로그, 메트릭, 트레이스, 디버그 출력을 고른다.
4. `재현`: 수정 전 실패하는 테스트, 요청, 조작을 만든다.
5. 한 번에 한 원인을 수정한다.
6. 같은 환경과 입력에서 재검증한다.

행동과 변경은 아래처럼 구분해 진행 중 업데이트와 최종 보고에 밝힌다.

- `관측`: 가설 판별용 계측이다. 제품 수정으로 세지 않는다.
- `재현`: 증상을 안정적으로 드러내는 실패 경계다.
- `진단 계측`: 원인 확인용 임시 로깅이다. 신호를 얻은 뒤 잔존 필요성, 수준, 민감정보, 제거 여부를 판단한다.
- `원인 수정`: 잘못된 상태나 계약이 처음 만들어지는 지점을 고친다.
- `완화`: 재시도, 가드, 폴백으로 영향을 줄이지만 원인이 남을 수 있다.
- `우회`: 문제 경로를 건너뛴다. 임시성, 제거 조건, 남은 원인을 함께 적는다.

`근본 해결`은 수정 전 재현이 실패하고 수정 후 같은 조건에서 통과하며, 관측 근거가 가설의 인과를 지지할 때만 쓴다. 재현 없이 방어 코드만 넣었거나 증상만 사라졌다면 `증상 해소 · 원인 미확정` 또는 `완화`라고 판정한다.

## 모바일 출력 형식

- 본문과 상태 보고 사이에 `◤◤◤◤◤◤◤◤` 한 줄을 둔다.
- 각 항목은 40자 안쪽 한 줄로 쓴다.
- 길면 문장을 뭉개지 말고 `·`로 나눈다.
- 코드 펜스와 긴 괘선을 쓰지 않는다.
- 테스트가 길면 `입력` 또는 `동작`, `기대`를 별도 줄로 둔다.

아래 골격을 유지한다.

◤◤◤◤◤◤◤◤

**작업 좌표**

███░░ 60%

- **목표** 여러 세션의 북극성
- **현재** 도달 수준 · 근거 · 남은 거리
- **다음** 가장 가까운 행동 하나
- **테스트**
  - 입력 `그대로 복사할 프롬프트`
  - 기대 관측 가능한 동작
- **결과**
  - `[파일](/절대/경로)`
  - `[공백 경로](</절대/경로 with spaces>)`
  - `[PR](https://github.com/org/repo/pull/1)`
